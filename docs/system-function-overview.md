# DraftRefine 系统功能说明文档

## 1. 一句话介绍

DraftRefine 是一个面向论文作者的“改稿闭环工作台”。它不是代写工具，而是帮助用户把已有论文草稿拆成章节，诊断问题，生成局部改写候选，处理导师或审稿人意见，并保留每一次修改记录。

更简单地说：用户已经有草稿，系统帮助他把草稿改得更清楚、更学术、更方便交给导师或审稿人继续审阅。

## 2. 系统定位

DraftRefine 的核心定位是“论文改稿与修订管理”，重点解决论文修改过程中最常见的几个问题：

- 草稿已经写出来了，但不知道哪里最需要先改。
- 导师或审稿人给了很多意见，但意见分散，难以转成具体任务。
- AI 能改文字，但用户不放心直接覆盖原文。
- 修改过很多轮以后，不知道哪一版来自自己手改，哪一版来自 AI。
- 论文不是一次生成出来的，而是需要反复诊断、局部修改、确认和回看。

因此，DraftRefine 不强调“帮你生成整篇论文”，而强调“帮你掌控改稿过程”。

## 3. 适用用户

系统主要面向以下几类用户：

- 正在写毕业论文、硕士论文、博士论文的学生。
- 已经有论文初稿，但需要提高结构、语气、逻辑和表达质量的作者。
- 收到导师批注，需要逐条消化修改意见的学生。
- 准备投稿或返修英文稿件，需要处理审稿意见的研究者。
- 希望保留修改痕迹，而不是让 AI 直接覆盖全文的谨慎型用户。

## 4. 核心价值

DraftRefine 的价值不在于“替用户写论文”，而在于让用户在论文修改中更有控制感。

- 它把一篇长文拆成可处理的章节，降低改稿压力。
- 它先诊断，再建议下一步，避免用户盲目改全文。
- 它只对当前章节生成候选改写，不会自动改完整篇。
- 它要求用户接受或拒绝 AI 候选，用户始终掌握最终文本。
- 它把导师意见变成任务，并映射到具体章节。
- 它记录版本历史，方便用户回看、对比和恢复。

## 5. 典型使用流程

完整流程可以概括为：

```text
上传或粘贴草稿
-> 系统解析章节
-> 生成诊断问题
-> 用户选择一个章节
-> 使用改写动作生成候选文本
-> 用户对比原文和候选
-> 接受或拒绝改写
-> 导入导师意见并任务化
-> 按意见继续局部修改
-> 查看版本历史或恢复旧版本
-> 导出章节或项目文本快照
```

这个流程强调“闭环”：不是给一个建议就结束，而是从草稿进入，到诊断、修改、确认、意见处理、版本回看都能串起来。

## 6. 系统主要功能

### 6.1 项目台

项目台用于管理所有论文改稿项目。

用户可以在这里看到：

- 当前项目标题和文档类型。
- 项目当前状态，例如待诊断、改稿中、待处理意见、可导出。
- 未解决诊断问题数量。
- 未完成导师意见数量。
- 待确认的 AI 改写数量。
- 系统建议的下一步动作。

项目台的作用是让用户不用打开每篇论文，就能知道“我现在最应该先处理哪个项目”。

### 6.2 新建改稿项目

用户可以通过两种方式创建项目：

- 上传已有论文文件。
- 直接粘贴草稿正文。

当前支持的文件类型包括：

- `txt`
- `docx`
- `pdf`

上传文件后，系统会尝试解析正文并生成章节。如果文件解析不理想，用户仍然可以通过粘贴正文继续进入流程。

新建项目时，用户还可以填写：

- 项目标题。
- 文档类型。
- 中文优先或英文优先。
- 本次最想解决的问题，例如先改研究问题、按导师意见补讨论、统一术语等。

### 6.3 章节解析

系统会把论文草稿拆分为章节，形成后续编辑和诊断的基础。

章节解析会尽量识别：

- Markdown 标题，例如 `# 研究背景`、`# 方法设计`。
- Word 文档中的段落文本。
- PDF 文件中提取出的页面文本。
- 没有明显标题时，系统会使用默认章节结构进行兜底拆分。

每个章节会保存：

- 章节标题。
- 原始文本。
- 当前文本。
- 章节顺序。
- 解析置信度。
- 当前问题数量。
- 当前导师意见数量。
- 当前修订状态。

### 6.4 诊断控制台

诊断页不是简单列出问题，而是一个改稿控制台。

它会显示：

- 未解决诊断数量。
- 导师意见数量。
- 待确认改写数量。
- 章节树和每个章节的状态。
- 按严重程度和问题类型整理的问题列表。
- 每个问题对应的建议动作。
- 一键跳转到对应章节进行修改。

诊断类型包括：

- 结构组织问题。
- 学术语气问题。
- 证据支撑问题。
- 论证逻辑问题。
- 段落过渡问题。
- 术语统一问题。

诊断页的目标是回答用户最关心的问题：这篇草稿先改哪里？

### 6.5 章节编辑器

编辑器是系统的核心工作区，采用三栏结构：

- 左栏是章节树，用于切换章节并查看每章状态。
- 中栏是正文编辑区和对比视图。
- 右栏是改写动作面板和导师意见上下文。

用户可以直接手动编辑当前章节文本。手动保存后，系统会生成一条“用户手改”的版本记录。

编辑器当前提供 6 类动作：

- 学术化改写：提升学术语气，减少口语化表达。
- 精简表达：压缩重复内容，保留段落主干。
- 扩展论述：补强论点承接，让章节更完整。
- 统一术语：减少同一概念在不同段落中的表达漂移。
- 按导师意见修改：结合当前章节相关意见生成定向修改。
- 插入过渡句：增强段落之间的衔接。

每次 AI 动作只作用于当前章节，不会直接改完整篇论文。

### 6.6 候选改写与接受机制

系统不会把 AI 输出直接覆盖正文，而是先生成“候选改写”。

候选改写会包含：

- 改写后的章节文本。
- 本次修改摘要。
- 使用的动作类型。
- Prompt 版本。
- 模型名称。
- 风险提示或警告。

用户可以在对比视图中查看原文和候选文本，然后选择：

- 接受改写：候选文本成为当前章节正文，并写入版本历史。
- 拒绝改写：关闭候选文本，保留用户当前正文。

这个机制保证“用户文本是当前真源”，AI 只是提供候选，不替用户做最终决定。

### 6.7 导师意见任务台

导师意见任务台用于把导师或审稿人的评论变成可执行任务。

用户可以粘贴一条导师意见，系统会尝试：

- 保存原始评论。
- 自动判断这条评论对应哪个章节。
- 给出映射置信度。
- 生成建议动作。
- 标记任务状态。

任务状态包括：

- 待处理。
- 处理中。
- 已完成。

如果系统自动映射不准确，用户可以手动改绑到正确章节。这一点很重要，因为导师意见常常写得比较口语化，完全自动判断容易让用户不信任。

用户可以从任务台直接跳转到对应章节，并带着这条意见执行“按导师意见修改”。

### 6.8 版本时间线

版本时间线用于记录论文修改过程。

系统会区分不同来源：

- 系统导入。
- 用户手动修改。
- AI 改写。
- 系统恢复。

每条记录会显示：

- 修改时间。
- 作用章节。
- 修改来源。
- 动作类型。
- 修改摘要。
- 模型和 Prompt 版本。
- 修改前文本。
- 修改后文本。

用户可以展开查看前后对比，也可以把某个历史版本恢复为当前文本。

恢复旧版本时，系统不会删除历史，而是新增一条“恢复版本”记录。这样能保证历史链条是可信的。

### 6.9 导出文本快照

编辑器支持导出：

- 当前章节文本。
- 当前项目文本快照。

导出格式目前是 `.txt`。这适合内测阶段快速保存改稿结果，但系统目前不承诺正式 Word 排版、参考文献排版或学校模板格式。

## 7. AI 与后端能力

系统由前端网页和轻量后端组成。

前端负责：

- 页面展示。
- 项目流程导航。
- 章节编辑。
- 候选改写确认。
- 任务台和版本时间线交互。

后端负责：

- 文件上传。
- 文本解析。
- 项目、章节、问题、评论、版本记录存储。
- LLM 调用。
- Prompt 加载。
- 模型调用日志记录。

当前后端使用：

- FastAPI 提供接口。
- SQLite 保存本地数据。
- 本地文件夹保存上传文件。
- YAML 文件管理 Prompt。
- DeepSeek 作为默认模型供应商。
- Qwen 作为备用模型供应商。

如果模型不可用，系统有基础规则兜底逻辑，保证流程还能跑通。但真正高质量的诊断和改写依赖可用的模型 API。

## 8. Prompt 工程设计

系统没有把 Prompt 写死在前端组件里，而是放在后端的 Prompt registry 中。

Prompt 按任务分类：

- 诊断 Prompt。
- 改写 Prompt。
- 导师意见映射 Prompt。

每次模型调用会尽量返回结构化 JSON，便于系统落库和前端稳定展示。

系统会记录模型调用日志，包括：

- 调用动作。
- Prompt 版本。
- 模型名称。
- 调用状态。
- 延迟。
- token 粗略估计。
- 输入哈希。
- 输出哈希。
- 错误信息。

这些日志后续可以继续接入 Langfuse、Helicone 或其他观测平台。

## 9. 当前已经实现的接口

当前后端已经提供以下核心接口：

| 接口 | 作用 |
| --- | --- |
| `GET /api/health` | 检查后端服务是否可用 |
| `GET /api/projects` | 获取项目列表 |
| `GET /api/projects/:id/bundle` | 获取项目、章节、问题、评论和版本记录 |
| `POST /api/projects` | 创建项目 |
| `POST /api/projects/:id/files` | 上传项目文件 |
| `POST /api/projects/:id/diagnose` | 生成诊断问题 |
| `POST /api/sections/:id/rewrite` | 对当前章节生成改写候选 |
| `POST /api/sections/:id/manual-edit` | 保存用户手动修改 |
| `POST /api/comments/import` | 导入导师或审稿人意见 |
| `POST /api/comments/:id/remap` | 手动重映射评论到章节 |
| `POST /api/comments/:id/status` | 更新评论任务状态 |
| `POST /api/issues/:id/status` | 更新诊断问题状态 |
| `POST /api/revisions/:id/accept` | 接受 AI 改写候选 |
| `POST /api/versions/:id/restore` | 恢复历史版本为当前文本 |
| `GET /api/jobs/:id` | 查询解析或诊断任务状态 |

## 10. 可以怎么对别人讲

如果只有 30 秒，可以这样讲：

> DraftRefine 是一个论文改稿工作台。它不是帮学生代写整篇论文，而是让用户上传已有草稿后，系统自动拆章节、诊断问题，并针对当前章节给出可接受或拒绝的改写候选。导师意见也可以导入成任务，系统会帮忙映射到章节，最后所有手改、AI 改写和恢复记录都会进入版本时间线，保证修改过程可追踪。

如果有 3 分钟，可以这样讲：

> 很多人写论文真正痛苦的地方不是完全不会写，而是草稿已经有了，却不知道怎么改。导师会说结构不清、论证不够、语气不学术，但这些意见很难直接变成可执行任务。
>
> DraftRefine 解决的是这个“改稿闭环”。用户上传 docx、pdf、txt，或者直接粘贴草稿。系统先把草稿拆成章节，再做诊断，告诉用户哪些章节存在结构、语气、证据、逻辑、过渡或术语问题。用户进入编辑器后，不是和 AI 随便聊天，而是通过动作面板选择学术化改写、精简、扩写、统一术语、按导师意见修改等操作。
>
> 每次 AI 只改当前章节，并且先生成候选文本。用户可以对比原文和候选，确认后才接受。接受后会进入版本历史；不接受就保留原文。这样用户始终掌握最终文本，不会被 AI 直接覆盖。
>
> 另一个重点是导师意见任务台。用户可以把导师或审稿人的原始评论粘贴进来，系统会映射到对应章节，生成建议动作，并允许用户手动改绑。后面用户可以逐条处理意见，最后通过版本时间线看到哪些内容是系统导入、哪些是自己手改、哪些是 AI 改写、哪些是恢复旧版本。
>
> 所以它的定位不是代写工具，而是一个更可信、更可控的论文改稿工作台。

## 11. 当前版本边界

当前版本适合单人真实内测，但还不是完整生产系统。

已经支持：

- 本地网页使用。
- 上传和粘贴草稿。
- 基础章节解析。
- 诊断问题生成。
- 当前章节局部改写。
- 接受或拒绝候选改写。
- 导师意见导入、映射和重映射。
- 版本历史和恢复。
- 文本快照导出。
- DeepSeek 和 Qwen 模型供应商配置。
- Prompt 版本管理和模型调用日志。

暂不支持：

- 多用户账号体系。
- 云端正式部署后的权限管理。
- 多人协作批注。
- 查重。
- 引用真实性核验。
- 自动文献检索。
- 学校 Word 模板排版。
- 一键生成完整论文。
- 正式投稿文件打包。

这部分边界可以主动讲清楚，反而会让系统显得更专业：DraftRefine 专注改稿，不包装成万能论文工具。

## 12. 演示建议

对外演示时建议按下面顺序：

1. 打开首页，强调“只改已有草稿，不替代写整篇”。
2. 进入新建项目页，上传 `txt/docx/pdf` 或粘贴一段草稿。
3. 创建项目后进入诊断页，看章节树和问题列表。
4. 点击一个高优先级问题，进入编辑器对应章节。
5. 选择“学术化改写”或“精简表达”，生成候选。
6. 切换对比视图，说明用户需要接受后才会改正文。
7. 导入一条导师意见，展示自动映射和手动改绑。
8. 回到编辑器，选择“按导师意见修改”。
9. 打开版本时间线，展示用户手改、AI 改写和恢复记录。
10. 导出当前章节或项目文本快照。

这个演示路径能完整体现系统的关键词：草稿、诊断、局部改写、人工确认、导师意见、版本可信。

## 13. 启动方式

本地演示需要同时启动后端和前端。

后端命令：

```powershell
cd /d F:\Fucking\thesis-refine-hub
python -m backend.app
```

前端命令：

```powershell
cd /d F:\Fucking\thesis-refine-hub
npm run dev -- --host 127.0.0.1 --port 5173
```

浏览器访问：

```text
http://127.0.0.1:5173
```

如果页面显示“无法访问此页面”或 `ERR_CONNECTION_REFUSED`，通常是前端或后端命令行窗口被关闭了，需要重新启动。
